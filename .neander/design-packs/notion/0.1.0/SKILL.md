# Notion-inspired document workspace

Import `NotionFramework` and the single `pack.css` entry from this pinned pack; it includes generated `tokens.css`. `NotionPrimitives` and `NotionChrome` compose adapted official shadcn Button, Command, Popover, Dropdown, and Dialog foundations. Use only customer-requested pages and controls. The customer request owns content, permissions, search results, persistence, and business rules. Preview fixtures are never application defaults.

Pass authoritative pages and selected page ID through the model. Implement `onCreatePage`, `onSelectPage`, and `onUpdatePage` through the host. Supply workspace, user, share, and page action models/callbacks only when requested and backed by real host behavior. Page moves, icons, favorites, links, and sharing use host callbacks; the framework preserves drafts on save failure and displays the failure. Install the pack's declared npm dependencies in the generated React project. Do not import Neander's own frontend components. Keep the `notion-pack` class and `data-ui-pack="notion"` on the framework root; portaled overlays carry the same pack marker. Do not add global shadcn theme overrides.

For a requested database surface, supply a page's `database` model with host-selected database view, columns, rows, and groups. The host owns schema, record creation/opening and persisted view settings; local filters and sorts operate on the supplied rows. `NotionDatabase` uses the shadcn Tabs/Radix pattern. Do not synthesize database content or expose controls without actions.

Use the adapted pinned shadcn controls in `components/react/ui/` whenever a corresponding control exists. `NotionButton` delegates to that Button with a ghost default; use `variant="default"` for primary actions. Import only `pack.css`; it includes tokens and the shared foundation. New product surfaces compose those controls. Recurring control changes belong in `ui/foundation.css` and `tokens.json`, not repeated surface resets. `NotionFramework` supplies the theme context; standalone compositions must use `NotionThemeProvider` so portals receive the correct active pack theme.

For the Notion navigation structure, supply only requested sections through `model.navigation`; use `onNavigate`/`onStartChat` for host-owned destinations. Keep `primaryActiveId` independent from the open page. Home owns the workspace tree; Chat uses `agentShortcuts`/`history`, Meetings uses `meetings`, and Inbox uses `inboxContent`. Supply capability flags and `onCreateMeeting(mode)` for accepted meeting creation; handle calendar connection through `onNavigate`. Do not reintroduce app promotions. Do not bake screenshot trial copy or sample workspaces into customer applications. Reuse `NotionSortList`/`NotionSortItem` for page and block sorting. Keep sidebar drag grips absent and document controls limited to plus/grip. The grip handles drag and click-to-open block actions. `onMoveFavorite` controls favorite order independently of `onMovePage`; preserve both on rejection.

When a requested surface fits, reuse `NotionLibrary`, `NotionChat`, `NotionMeeting`, `NotionDashboard`, or `NotionAgentSettings` in the existing framework's `content`/`header`/`inspector` slots. Import only the requested compositions; never copy the reference preview or its branded assets/sample data into customer code. Use authoritative host props and callbacks for messages, recording state, agent execution, access, saving, and connected apps. Do not fabricate AI responses, transcripts, invitation delivery, or integration success. Keep the pinned font and chart dependencies declared by the manifest. The new surfaces inherit the same scoped theme and shadcn sources.

For linked-page/database creation, wire `onCreatePage` / `onCreateDatabase` and return the accepted resource ID. Use resource blocks with `referenceId` instead of rendering independent page or table markup. Represent records as pages with database `parentId` and matching row IDs. Keep row titles and property values synchronized through host callbacks. Wire side/center peek IDs and close callbacks so record opening preserves the source database. The framework guards navigation and peek closure with accepted saves; do not bypass it with direct route mutation from an editor.

Custom surface navigation must use `useNotionNavigationGuard()` so dirty record and cell drafts are saved before route changes. Reuse shared database schema controls, tag tones, search Dialog, Trash and record chrome; do not fork table and record property editors. See the React README for the controlled view, draft and restore callbacks.

For requested workspace flows, use NotionHome, NotionSettings, NotionInbox, NotionTemplates, NotionDiscussions and NotionVersionHistory. Reuse controlled comment drafts, accepted settings/history callbacks and the shell navigation guard. Settings extension slots are host-owned, not complete admin/billing implementations. Do not enable account, OAuth or connected service actions without real callbacks.

Database layouts include table/board/list/gallery/calendar/timeline/feed/chart/form. Reuse NotionDatabase, typed schema controls and the same record pages across all views. Linked database blocks reference the original database and keep a separate selected view. Board moves must update grouping property values in every view. Formula/rollup display consumes host-computed values; no expression engine is supplied. Use existing structured-block payloads, cover and media callbacks; do not invent separate persistence paths. See the React README for signatures and the QA report for limitations.

Wire supported values to model.preferences so changes affect calendars, composing keys, numeric display and text-direction controls. Do not treat saved preferences as decorative labels.
